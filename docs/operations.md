# Restarts and recovery

Restart the connector from Matrix, understand what survives a restart, and recover a failed update. Host commands on this page run from the instance directory.

[Back to Riftjack](../README.md)

The initial owner (`MATRIX_OWNER_ID`) can send **`!restart`** in an encrypted DM with a Codex bot, Claude bot, or the manager, or in an explicitly linked encrypted shared room. This restarts the entire connector and all bots, preserving accounts, encryption keys, files, and conversation pointers. Added accounts cannot restart it. The command is handled locally, without calling a model or changing its permissions. In a shared room, the first authorized local bot to handle the event claims it for the whole connector: only that bot acknowledges or refuses the command. Copies received by other bots, including after a restart, are ignored. If the command is refused or its acknowledgement fails, send a new command to retry.

## Reloading the supervisor

Use **`!restart supervisor`** to explicitly reload the supervisor as well, even when its code has not changed. The host supervisor waits for the connector to exit, then launches a fresh supervisor in its own environment; no process is launched by the sandboxed coding agent. The old supervisor remains only as a signal-forwarding parent, so its outer PID can remain visible. The same owner-only, idle-task and acknowledgement requirements apply, and the startup notice returns to the requesting room/thread. This command requires a supervisor that advertises support; an older one refuses it without stopping any bots. For initial activation, run `riftjack/scripts/restart-supervisor.sh` once from the instance directory in the host terminal. The script verifies that the new supervisor module loads, limits process selection to supervisors running in this instance directory, respects `DATA_DIR`, and waits for old supervisors and the connector lock to disappear before launching the replacement. It does not remove stale locks or kill supervisors of other instances. To start manually without the script, stop the current host process and run `npm --prefix riftjack start` again.

## Restart sequence

`npm --prefix riftjack start` runs a small supervisor. After the restart acknowledgement is successfully sent to Matrix, the connector stops; the supervisor waits for the old process to exit and then starts a new one. The replacement reloads source files and `.env` (environment variables inherited from the launching shell still take precedence). New tasks are blocked once the restart is accepted. If any bot is working or an account is being started/created, restart is refused: wait, or send `!cancel` in the active conversation and retry after it stops. Messages sent during the restart gap are ignored by the normal startup rule.

Before acknowledging `!restart`, the connector saves the requesting bot, owner, room and message/thread in `data/restart-notice.json` (under `DATA_DIR` when customized). After startup completes, that same bot sends an encrypted “Connector restarted” reply there, including the number of bots online. Pending notices survive process replacement. Network failures are retried every 30 seconds using the same Matrix transaction ID to prevent duplicate messages; the notice is removed after delivery. If the requesting bot fails to start, the notice remains for a later successful startup. Access and encrypted room membership are checked again before sending. An ordinary start with no pending restart sends no notice.

To enable `!restart` after upgrading from the old launcher, stop the running connector on the host once, then run `npm --prefix riftjack start`. Starting `src/main.ts` directly does not provide restart support. Ctrl+C or SIGTERM to the supervisor stops the connector without restarting it. `data/connector.pid` continues to identify the child connector process, not its supervisor.

## Crash recovery and rollback

If the connector exits unexpectedly, the supervisor starts it again after a delay that grows from 1 s to 60 s on consecutive failures. It does not restart after a normal shutdown (exit code 0) or an invalid `.env` (exit code 78). A connector counts as working once its bots are online and it has kept running for 30 seconds; the supervisor then promotes the snapshot captured before that process launched to `.connector-history/good-*` if it differs from the last working version (the last 10 versions are kept). The snapshot contains `src/`, `package.json`, `package-lock.json` and `tsconfig.json`; later edits on disk are not included. If the files change during startup, before the ready signal, that run creates no working snapshot. Pending launch snapshots are discarded when the child exits and are never used for rollback. If the connector crashes before reaching that point and its code differs from the latest working snapshot, the supervisor moves the current code to `.connector-history/failed-*` and restores the snapshot. When this follows `!restart`, the owner who requested it receives the rollback explanation in the usual restart notice. A rollback after an ordinary crash is reported to the owner in the Bot Manager DM once the manager is back online. `node_modules` is never changed by rollback; run `npm --prefix riftjack ci` yourself if dependencies differ. If the supervisor's own code (`supervisor.ts`, `restart.ts`, `restart-notice.ts`, `history.ts`, `errors.ts`) changed since it started, `!restart` also starts the updated supervisor: the running one launches it as a child and only forwards signals, so its PID, terminal and log stay the same. If the running supervisor predates automatic self-reload, relaunch it on the host.
